Boosting tree and lexicon matching for Whisper

published 2026-11-05

2 The problem and its constraints

Keyword boosting is the set of techniques that hand a speech-to-text model a list of rare words at run time, so that it writes them when they are said. This report covers two of them for Whisper, the speech-to-text model that takes the audio of an utterance and writes its transcript, and a variant of the second. Each one is read against the problem below.

The words to recover

A keyterm is a word or phrase that is rare in Whisper's base vocabulary: a street name (rue de Rivoli), a weapon (Kalachnikov), a military vehicle (Leclerc, Griffon), a unit. The lexicon is the list of keyterms given to the model for a mission. The requirements ask that it hold at least 500 to 1,000 entries: every technique has to work at that size, and may be given more.

Most of those entries are not said in a given utterance, the stretch of speech, a few seconds long, that is transcribed as one unit. A mission anticipates many words and uses a subset. A keyterm of the lexicon that is not spoken in the utterance is a distractor keyterm. With 1,000 keyterms and one or two said per utterance, nearly the whole lexicon is distractor keyterms for any one utterance, and every technique below has to recover the spoken keyterms without writing the others.

The output is the transcript, the text Whisper writes for one utterance. The goal is a transcript that holds the keyterms that were spoken, spelled as in the lexicon.

Where the techniques act

flowchart LR
  A["audio of one utterance<br/>+ lexicon of at least 500–1,000 keyterms"] --> W["Whisper writes<br/>(technique 1 acts here)"]
  W --> T1["transcript"]
  T1 --> P["correction of the text<br/>(technique 2 acts here, if time allows)"]
  P --> T2["transcript with the spoken keyterms"]

The first technique acts while Whisper writes, inside its decoding. The second corrects the transcript once Whisper has written it, with no access to the audio. In the sprint the two run one after the other on the same utterance, the first one built first, the second one used if time allows. The report explains both in full either way, with what the literature measures for each and the code that exists. Finding implementations is a plus, not a requirement.

The constraints

Constraint What it fixes
A GPU on Ultron Ultron is the field system that records and transcribes during an exercise. Whisper runs there on a GPU, and the deliverable must work there.
About 3 s per utterance The transcript may arrive at most about 3 s after the utterance ends.
At least 500 to 1,000 keyterms A lower bound set by the requirements, not a ceiling. With distractor keyterms, since only a subset of the lexicon is spoken.
The finetuned Whisper as the base Our Whisper finetuned on mission data, used in mission today. Its WER is fairly good.
The sprint Three weeks from 2026-11-04 to deliver a first version that works on Ultron.

WER (word error rate) is the share of the reference's words that the transcript gets wrong: substituted, deleted or inserted, divided by the number of reference words.

The report covers the algorithms only. faster-whisper, the Python runtime that runs Whisper on Ultron, is set aside: how it could run these techniques is a separate question, left for later.

12 Implementations of the boosting tree

The boosting tree exists as code in several speech toolkits, none of them built for Whisper. What exists for Whisper is the hook to plug one in.

Code Runtime Models Tree, withdrawal, end of transcript Boosting weight

The Whisper paper of section 11 publishes no code. A Rust crate for Whisper, whisper-apr, and one for an RNN-T engine, gigastt-core, describe a prefix tree over keyterm tokens with a weight added to the tokens that continue a match; their withdrawal and their use in beam search were not checked for this report.

What the libraries share shapes a Whisper version. icefall's ContextGraph is a single Python file of about 600 lines, half of it drawing and tests, with no dependency on a decoder: it takes token IDs and returns, for one position and one token, the score change and the next position. That is the tree, the failure links and the withdrawal of sections 6, 7 and 9. The part left to write is the Whisper side: a logits processor that keeps one position per hypothesis, follows beam search when it reorders and forks hypotheses, adds the score changes of every candidate token, and treats the end-of-text token as a transition out of the tree.

SequenceBiasLogitsProcessor is the shortest route to a test and the furthest from the technique. Its documentation advises beam search and biasing the prefixes of each sequence too, which gives the first tokens a weight that is never taken back.

18 Implementations of lexicon matching

Lexicon matching exists as code in pieces: libraries for each stage, scoring by spelling, phonetic codes, G2P and indexes, and no library that runs the whole of it on a transcript with a lexicon. Every piece below runs on the CPU and needs no GPU.

Code Stage What it gives Language
RapidFuzz scoring by spelling, brute force process.extract, extractOne and cdist score one span or many against a whole lexicon, with Levenshtein, Damerau-Levenshtein, Jaro-Winkler and others; score_cutoff is the match threshold; compiled, workers=-1 uses every core any
symspellpy (SymSpell) retrieval by spelling an index of the strings a few deletions away from each keyterm, queried within k edits; lookup_compound and word_segmentation also undo split and merged words any; the lexicon is a word list
pybktree retrieval by spelling a BK-tree in pure Python: BKTree(distance, items).find(span, k) any
abydos phonetic code a large set of rule-based phonetic codes, French ones included (FONEM, HenryEarly), and many string distances French and others
jellyfish phonetic code, scoring Soundex, Metaphone, NYSIIS, Jaro-Winkler, Levenshtein English codes only
phonemizer with eSpeak NG G2P text to phonemes in IPA, with a French voice; the phoneme strings then go to RapidFuzz for an edit distance on sound French and others
NeMo SpellMapper the whole correction, trained retrieval by character n-gram mappings, then a trained model that picks the keyterm and its span; the code and an English model are public English model only

Assembled for the sprint, the rule-based version is a short script around these libraries: text normalization of the transcript and the lexicon, the sliding window over word n-grams, retrieval through RapidFuzz on the whole lexicon (at 1,000 keyterms no index is needed) or a character n-gram index, a score by spelling and one by sound on the phonemes of the span and the keyterm, the match threshold, and the choice between overlapping matches. The phonemes of the 1,000 keyterms are computed once per lexicon; those of the spans are computed per utterance, the step whose time to measure first against the 3 s.

The parts no library gives are the ones that decide the result on the mission's words: the threshold, its guards against ordinary words, and the check that the French phonetic code or eSpeak NG handles the lexicon's foreign names.

The boosting tree fits the constraints the papers measured: run time, lexicon size and distractor keyterms. What no paper measured is the finetuned Whisper and French, which the sprint's own experiments settle, a vanilla Whisper first and the finetuned Whisper after. Its work is in code: the logits processor of section 8 and the boosting weight's tuning.

Lexicon matching fits the GPU and the 3 s, and the lexicon size is where it is weakest. Its work is in the match threshold, the guards and the phonetic code, all tuned on the mission's words, so it is the one that fits after the boosting tree if time allows.

The correction memory fits every constraint of computation, and its gain depends on what operators correct and mark over the exercises, which a three-week sprint can build but cannot yet measure. In sequence after the two others it adds no run time worth counting.
